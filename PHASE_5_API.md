# FlakeLedger Phase 5 API & Postgres Documentation

## Local Development Setup

To run the API locally, you need a PostgreSQL database.
Create a `.env` file in the root of the project:

```env
PORT=4000
DATABASE_URL=postgresql://user:password@localhost:5432/flakeledger
FLAKELEDGER_API_URL=http://localhost:4000/api/v1
```

Run the API Server:
```bash
npx tsx src/server.ts
```

*Note: The server will automatically run schema migrations (CREATE TABLE IF NOT EXISTS) when booting up.*

To run the CLI so that it connects to the API instead of using `.flakeledger/experiments/`, ensure `FLAKELEDGER_API_URL` is set in your `.env`.

## Database Model

The relational database is structurally modeled using three highly decoupled tables designed for append-only operations:

- **`experiments`**: 
  - `id` (Primary Key)
  - `target`, `status`, `config` (JSONB)
  - Records the high-level orchestrational intent.
- **`observations`**:
  - `id` (Primary Key: uniquely constructed as `experimentId-conditionId-runNumber` to guarantee idempotency and deduplication)
  - `experiment_id` (Foreign Key -> experiments.id)
  - `process_status`, `duration_ms`
  - `test_results`, `environment` (JSONB)
  - Strictly stores append-only raw evidence generated by Vitest.
- **`diagnoses`**:
  - `experiment_id` (Primary Key -> experiments.id)
  - `classification`, `confidence`, `explanation` (JSONB), `evidence` (JSONB)
  - Completely derived output artifact. Purely deterministic representation of observations.

## Migration Process

If you possess Phase 4 `.flakeledger/experiments/` local JSON files, you can seamlessly push them into PostgreSQL:

```bash
# Ensure the API is running locally and FLAKELEDGER_API_URL is configured
npx tsx src/index.ts migrate
```
The CLI will iteratively `POST` the existing metadata, push observations, and trigger the remote server to deterministically generate a Postgres-backed `Diagnosis`. No local files are dropped, providing a robust offline fallback.

## API Architecture

The system uses standard HTTP REST via Express. 
Business logic and mathematical deductions live solely in the `ExperimentService` and `analyzeExperiment` pure functions. HTTP routes are completely thin and contain no SQL.

## Endpoints

### 1. Health
`GET /api/v1/health`
Returns the status of the server.
**Response**: `200 OK`
```json
{ "status": "ok", "database": "reachable" }
```

### 2. Create Experiment
`POST /api/v1/experiments`
Create an experiment configuration.
**Request**: `ExperimentConfig` object.
**Response**: `201 Created` (`ExperimentMetadata`)

### 3. List Experiments
`GET /api/v1/experiments`
Lists all known experiments ordered by creation time.
**Response**: `200 OK` (`ExperimentMetadata[]`)

### 4. Get Experiment Metadata
`GET /api/v1/experiments/:id`
**Response**: `200 OK` (`ExperimentMetadata`)

### 5. Push Observations
`POST /api/v1/experiments/:id/observations`
Insert an array of `Observation`s into the database. If the observation already exists, it is safely ignored due to idempotent database constraints.
**Request**: `Observation[]`
**Response**: `201 Created`

### 6. Get Observations
`GET /api/v1/experiments/:id/observations`
**Response**: `200 OK` (`Observation[]`)

### 7. Trigger Diagnosis
`POST /api/v1/experiments/:id/diagnose`
Commands the server to mathematically analyze all raw observations belonging to `:id` and persist a new derived `DiagnosisResult`.
**Response**: `201 Created` (`DiagnosisResult`)

### 8. Get Diagnosis
`GET /api/v1/experiments/:id/diagnosis`
**Response**: `200 OK` (`DiagnosisResult`)

## Error Responses

Errors are strictly localized to a standardized JSON schema and map semantically to correct HTTP codes (400, 404, 500). Internal SQL logs are stripped from user-facing JSON.

```json
{
  "error": {
    "code": "EXPERIMENT_NOT_FOUND",
    "message": "Experiment not found"
  }
}
```
