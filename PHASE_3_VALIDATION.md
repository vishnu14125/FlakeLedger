# Phase 3: Diagnosis Validation Report

### Implementation
- `src/diagnosis.ts`: Core deterministic classification logic (Condition metrics, delta math, hashing frequency).
- `src/index.ts`: Added the `diagnose <experiment-id>` CLI command.
- `test/diagnosis.test.ts`: Added 10 synthetic unit tests to cover every classification boundary and ambiguous cases.
- `PHASE_3_DIAGNOSIS.md` (new)

### Architecture
1. **Stored Observations**: Raw, immutable `EXP-*.json` files generated by Phase 2.5.
2. **Observation Aggregator**: Groups Pass/Fail/Timeouts by `conditionId`.
3. **Cross-Condition Comparison**: Finds the `minFailRate` and `maxFailRate` to calculate the effect size (`delta`).
4. **Failure Fingerprint Analysis**: Identifies the `dominantHash` across failures to measure error consistency.
5. **Evidence Scoring**: Derives confidence from sample size, delta magnitude, and hash consistency.
6. **Classification & Explanation**: Emits a `DiagnosisResult` mapping to a strict taxonomy.
7. **Persistence**: Saves to `<experiment-id>-diagnosis.json` without modifying the original observations.

### Classification Results (Real Benchmarks)
The diagnosis engine was run against the live Phase 2.5 dogfood observations:
- **Timezone Benchmark**: `ENVIRONMENT_SENSITIVE` (Confidence: HIGH)
- **Order Benchmark**: `ORDER_SENSITIVE` (Confidence: HIGH)
- **Concurrency Benchmark**: `CONCURRENCY_SENSITIVE` (Confidence: HIGH)
- **Intermittent Benchmark**: `INTERMITTENT` (Confidence: MEDIUM)
- **Stable Benchmark**: `STABLE` (Confidence: HIGH)

### Automated Tests
- **Unit Tests Passed**: 10
- **Unit Tests Failed**: 0
- Tested ambiguous boundaries (e.g., 50% baseline fail vs 50% parallel fail correctly outputs `INTERMITTENT`, ignoring the parallel condition because there is no differential jump).

### Confidence Model
- **HIGH**: >= 10 valid runs AND delta >= 0.8 (for sensitivity), OR >= 5 runs with 100% stable/deterministic behavior.
- **MEDIUM**: >= 5 valid runs AND delta >= 0.6.
- **LOW**: Delta < 0.6 or sample size is extremely small.
- **INSUFFICIENT**: < 3 valid test runs.

### False Positive Analysis
- **0 False Positives.** The engine successfully avoided diagnosing the Intermittent Benchmark as "Concurrency Sensitive" because it requires a large absolute delta (jump in failure rate) between conditions to trigger a sensitivity classification.

### False Negative Analysis
- **0 False Negatives.** The engine successfully triggered `CONCURRENCY_SENSITIVE` for the concurrency benchmark despite some baseline runs failing, because the absolute jump from baseline to parallel execution was massive.

### Limitations
- The classification relies on `conditionId` strings to map behavior to semantic categories (e.g. knowing that `concurrency-parallel` maps to Concurrency). While generic, this relies on user-provided config naming conventions.
- The engine establishes *behavioral association* but not *ast-level root cause*.
